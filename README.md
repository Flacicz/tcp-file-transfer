# TCP File Transfer

Учебный проект: консольные клиент и сервер для передачи файлов по TCP под Linux.
Язык — C11, сетевой API — системные POSIX-сокеты, сборка — CMake.

**Статус:** завершён второй промежуточный этап: клиент отправляет серверу
пять байтов `HELLO`, сервер получает их и проверяет содержимое. По сообщению
автора, сборка и штатный обмен в Linux/WSL прошли успешно. Автор также провёл
проверки неверного содержимого, накопления сообщения несколькими вызовами `recv`
и неполного сообщения. Передача файлов не реализована.

Ниже описаны требования к законченной первой версии и её планируемый интерфейс.
Текущее состояние, команды сборки и результаты проверок приведены в разделе
«Текущее состояние и ближайший шаг».

## Цель проекта

Разработать две консольные программы — клиент и сервер — для передачи содержимого
файла по TCP с компьютера клиента на компьютер сервера.

Практический результат: сервер сохраняет переданный файл в своей файловой системе
без изменения содержимого, а клиент сообщает пользователю результат передачи.

Учебная цель — освоить основы сетевого программирования на C под Linux.
На практике разобраться в следующих темах:

- создание сокетов, ожидание подключений и установление TCP-соединения;
- передача потока байтов и разработка простого протокола приложения;
- частичные чтения и записи, определение конца передачи и обработка обрыва;
- чтение и запись файлов порциями с ограниченным расходом памяти;
- обработка ошибок и управление временем жизни файлов и сокетов;
- сборка с предупреждениями компилятора и отладка с помощью GDB.

## Платформа и ограничения реализации

Целевая платформа первой версии — Linux. Язык программирования — C11, система
сборки — CMake. Для сетевого взаимодействия используются системные POSIX-сокеты.

Программы запускаются из терминала. Разработка и проверка могут выполняться
в Linux через WSL или в отдельной установке Linux.

Клиент и сервер обрабатывают файл небольшими порциями, не загружая его целиком
в оперативную память. Расход памяти на буферы передачи не должен расти
пропорционально размеру файла.

## Участники и интерфейс запуска

Сервер принимает подключения, получает файлы и сохраняет их. Клиент устанавливает
соединение с сервером, отправляет один файл и ожидает результат операции.

Сервер обслуживает клиентов последовательно: одновременно выполняется не более
одной передачи. Одно TCP-соединение используется для передачи одного файла.

Приведённые ниже команды описывают будущий интерфейс законченной первой версии.
Текущие программы `server` и `client` запускаются без аргументов; адрес `127.0.0.1`
и порт `9000` заданы в исходниках. Команды сборки и запуска текущего этапа приведены
в разделе «Текущее состояние и ближайший шаг».

```text
./server <порт> <каталог-сохранения>
./client <IPv4-адрес-сервера> <порт> <путь-к-файлу>
```

Каталог сохранения должен существовать до запуска сервера. Клиенту передаётся
числовой IPv4-адрес сервера.

Для проверки на одном компьютере сервер и клиент запускаются в разных терминалах.
После реализации передачи файлов пример запуска при уже существующем каталоге
`received` будет выглядеть так:

```text
./server 9000 ./received
./client 127.0.0.1 9000 ./photo.jpg
```

`127.0.0.1` — адрес локального компьютера. Для передачи между компьютерами клиенту
указывается IPv4-адрес машины с сервером.

## Основной сценарий

1. Пользователь запускает сервер, указывая порт и каталог сохранения.
2. Сервер подготавливается к работе и ожидает подключения.
3. Пользователь запускает клиент, указывая адрес сервера, порт и путь к исходному файлу.
4. Клиент подключается к серверу и передаёт размер файла, затем его содержимое.
5. Сервер получает содержимое и сохраняет его в новом файле.
6. После полного получения содержимого, успешного завершения записи и закрытия
   файла сервер отправляет подтверждение успеха.
7. Клиент получает подтверждение и сообщает пользователю об успешной передаче.
8. Обслуживание соединения завершается. Сервер возвращается к ожиданию следующего клиента.

Возвращение сервера к ожиданию не требует подтверждения от клиента о получении ответа.

## Протокол обмена

Поверх TCP используется простой протокол приложения: клиент отправляет размер,
затем содержимое файла. Сервер отвечает одним байтом статуса.

```text
Клиент → сервер: [размер: 8 байтов][содержимое: N байтов]
Сервер → клиент: [статус: 1 байт]
```

- Размер — беззнаковое 64-битное число `N` в сетевом порядке байтов
  (big-endian, старший байт первым).
- Содержимое — ровно `N` исходных байтов. Пустые файлы допускаются: для них `N = 0`,
  содержимое отсутствует.
- `0x00` — сервер полностью получил файл и успешно завершил его запись и закрытие.
- `0x01` — сервер сообщает об ошибке приёма или сохранения. При ошибке отправка
  этого статуса выполняется, если соединение ещё позволяет ответить.

Статус — числовое значение одного байта, а не текстовая строка.
Клиент считает передачу успешной только после получения `0x00` в ответ на полностью
отправленный файл. Отсутствие ответа означает, что успех не подтверждён: файл мог
быть сохранён, но ответ мог не дойти. Неизвестный статус считается ошибкой протокола.
Подтверждение означает успешное завершение файловых операций, но не гарантирует
сохранность данных при последующем сбое питания.

TCP предоставляет упорядоченный поток байтов и не сохраняет границы отдельных
отправок. Поэтому программы должны учитывать частичные чтения и записи при
обработке размера, содержимого и статуса. Закрытие соединения до получения всех
ожидаемых байтов означает незавершённый обмен.

## Правила сохранения файлов

Сервер самостоятельно назначает каждому принимаемому файлу уникальное имя
с расширением `.bin`, например `received-000001.bin`. Точный способ формирования
имени выбирается при реализации.

Существующие файлы не должны перезаписываться, в том числе после перезапуска сервера.

Клиент не передаёт исходное имя, расширение и другие метаданные файла. Расширение
`.bin` используется только для имени сохранённого файла: содержимое не преобразуется,
его формат и кодировка не меняются.

При обнаруженной ошибке или обрыве передачи сервер закрывает и удаляет неполный
файл. Если закрытие или удаление завершается ошибкой, сервер сообщает об этом
в диагностике.

## Обработка ошибок и управление ресурсами

Каждая программа выводит понятные сообщения о своих ошибках в свой терминал.

Некорректные аргументы запуска препятствуют началу работы соответствующей
программы. Сообщение должно объяснять причину ошибки и ожидаемый формат запуска.

Должны обрабатываться ошибки открытия, чтения, записи и закрытия файлов,
установления соединения и обмена данными, а также преждевременное закрытие
соединения другой стороной.

Ошибка отдельной передачи не должна без необходимости завершать сервер.
После завершения обработки такой ошибки сервер должен продолжать принимать
подключения, если дальнейшая работа возможна.

На всех обрабатываемых путях завершения открытые файлы и сокеты должны
освобождаться. Для каждого файлового дескриптора должно быть определено,
какая часть программы отвечает за его закрытие.

Автоматическая повторная отправка и возобновление передачи после обрыва
в первой версии не реализуются. Пользователь может запустить клиент повторно;
такая отправка считается новой передачей.

## Границы первой версии

В первую версию не входят:

- одновременное обслуживание нескольких передач;
- автоматические повторные попытки и возобновление передачи после обрыва;
- передача исходного имени файла и других метаданных;
- авторизация и шифрование;
- доменные имена, IPv6 и поддержка Windows-сокетов;
- графический интерфейс и сторонние сетевые библиотеки.

## Критерии готовности

Первая версия считается готовой, когда подтверждено следующее:

- Пустой файл, бинарный файл и файл значительно больше буфера передаются без
  изменения содержимого. Результат проверяется через `cmp` или контрольные суммы.
- Клиент сообщает об успехе только после получения предусмотренного протоколом
  подтверждения в ответ на полностью отправленный файл.
- Обрывы при передаче размера, содержимого и ожидании подтверждения распознаются
  и сопровождаются понятными сообщениями.
- Неполный файл удаляется при обработке ошибки сервером; невозможность удаления
  отражается в диагностике.
- Некорректные аргументы и ошибки файловых операций обрабатываются
  и сопровождаются понятной диагностикой.
- Существующие файлы не перезаписываются, в том числе после перезапуска сервера.
- После успешных и неудачных передач сервер принимает новые подключения.
- После завершения передач не накапливаются незакрытые файлы и сокеты.
- Проверки целевого поведения выполнены в Linux.
- Автор может объяснить используемые системные вызовы, правила протокола
  и обработку разобранных ошибок, а также воспроизвести эти ошибки.

## Текущее состояние и ближайший шаг

В репозитории реализован обмен коротким сообщением `HELLO`:

- В CMake описаны две исполняемые цели: `client` из `client/main.c`
  и `server` из `server/main.c`, с C11 и предупреждениями
  `-Wall -Wextra -Wpedantic`.
- Клиент подключается к `127.0.0.1:9000` и циклом отправляет ровно пять байтов
  `HELLO`, обрабатывая частичные отправки и `EINTR`, а также подавляя `SIGPIPE`
  флагом `MSG_NOSIGNAL`.
- Сервер принимает одно подключение, циклом накапливает пять байтов, обрабатывает
  частичные чтения, `EINTR` и преждевременное закрытие, затем сверяет сообщение
  с `HELLO` через `memcmp`.
- После одной передачи сервер закрывает соединение и завершается. Клиент и сервер
  пока не обмениваются ответом о результате проверки.
- Аргументы командной строки, передача и сохранение файлов, подтверждение сервера
  и повторное ожидание подключений ещё не реализованы.

По сообщению автора, текущая версия собрана и штатный обмен проверен в Linux/WSL.
Автор сообщил о выполнении проверок неверного содержимого, приёма сообщения
несколькими порциями и закрытия соединения после отправки двух байтов.
По сообщению автора, при отправке двух байтов сервер вывел сообщение о получении
двух из пяти байтов и завершился с ненулевым кодом. Временные изменения для
проверок удалены. Ветки `EINTR`, частичной отправки, отсутствия прогресса `send`
и очистки ресурсов рассмотрены по коду; обычная успешная передача сама по себе
не подтверждает их выполнение.

### Сборка и запуск текущего этапа

Команды выполняются из корня репозитория в Linux или WSL. Настройка CMake
создаёт отдельный каталог `build`, а следующая команда собирает обе программы:

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build --parallel
```

Запусти сервер в одном терминале:

```sh
./build/server
```

Затем во втором терминале из корня репозитория запусти клиент:

```sh
./build/client
```

При штатном обмене клиент сообщает об отправке пяти байтов в сокет, а сервер —
о получении и проверке `HELLO`. Сервер обслуживает только одно подключение
за запуск. Подробности реализации и проверок этапа приведены в
[architecture.md](architecture.md).

Перед новым этапом стоит оценить, сохранять ли завершённый обмен `HELLO`
отдельным коммитом, затем согласовать содержание следующего этапа.
