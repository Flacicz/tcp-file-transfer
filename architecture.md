# Архитектура проекта

## 1. Назначение и статус

Документ описывает реализованный третий промежуточный этап: передачу пяти
байтов `HELLO` и ответ сервера одним байтом статуса. Требования к законченной
первой версии находятся в README.md; передача файлов ещё не реализована.

По сообщению автора, сборка и проверки обмена выполнены в Linux/WSL.
Фактически выполненные проверки и проверки только по коду разделены ниже.

## 2. Границы текущего этапа

- Linux, C11, блокирующие TCP-сокеты поверх IPv4.
- Отдельные консольные программы клиента и сервера.
- Адрес `127.0.0.1` и порт `9000` заданы в исходниках.
- Сервер принимает одно подключение, обрабатывает его и завершается.
- Клиент отправляет `HELLO`, затем ожидает результат проверки.
- Аргументы запуска, передача файлов и повторное ожидание клиентов отсутствуют.
- Тайм-аутов нет: при открытом соединении ожидание данных или ответа может
  продолжаться без ограничения времени.

## 3. Протокол текущего этапа

```text
Клиент → сервер: HELLO (48 45 4C 4C 4F)
Сервер → клиент: статус (1 байт)
```

Клиент отправляет ровно пять байтов ASCII, без завершающего нуля строки C,
перевода строки и поля длины. Сервер получает пять байтов и сравнивает их
с `HELLO`; дополнительного чтения для ожидания EOF или проверки лишних байтов нет.

Статус имеет тип `uint8_t` и передаётся как числовой байт:

- `0x00` — сервер полностью получил и проверил `HELLO`.
- `0x01` — сервер получил пять байтов, но содержимое не совпало с `HELLO`.
- Другое значение — ошибка протокола для клиента.

После полной отправки сообщения клиент считает проверку успешной только при
получении `0x00`. Отсутствие ответа означает, что успех не подтверждён:
сервер мог обработать сообщение, но ответ мог не дойти. Статус относится
только к проверке сообщения, а не к сохранению файла.

TCP предоставляет упорядоченный поток байтов и не сохраняет границы вызовов
отправки. Успешный `send` означает приём данных локальной системой для отправки,
но не подтверждает их обработку другой программой. Дополнительного ответа
клиента на статус нет.

## 4. Исходники и сборка

- `client/main.c` — `main` клиента и функция `receive_status`.
- `server/main.c` — `main` сервера и функция `send_status`.
- `CMakeLists.txt` — цели `client` и `server`, C11, предупреждения
  `-Wall -Wextra -Wpedantic`.

Используется Debug-сборка в отдельном каталоге. Команды приведены в README.md.
Общие модули, дополнительные библиотеки и динамическая память не требуются.

## 5. Последовательность работы сервера

1. Подготовить IPv4-адрес, создать сокет, выполнить `bind` и `listen`.
2. Дождаться подключения через `accept`, повторяя его при `EINTR`.
3. Сохранить `connection_fd` отдельно от `listen_fd`.
4. Циклом `recv` накопить ровно пять байтов, учитывая частичный приём и `EINTR`.
5. При EOF до пяти байтов или ошибке приёма вывести диагностику и перейти
   к `cleanup`, не отправляя статус.
6. Сравнить полученные байты с `HELLO` через `memcmp`.
7. При совпадении отправить `0x00`; при несовпадении вывести диагностику,
   установить ненулевой `exit_code` и попытаться отправить `0x01`.
8. Проверить результат отправки, закрыть оба сокета и завершить программу.

Для обмена используется сокет соединения, полученный от `accept`.
Слушающий сокет нужен для приёма подключений. Адрес клиента не извлекается.
Параметр `backlog` ограничивает очередь ожидающих принятия подключений,
а не количество обслуживаемых программой клиентов.

Приёмный буфер не содержит завершающего нуля и не выводится через `%s`.

## 6. Последовательность работы клиента

1. Подготовить адрес сервера, создать сокет и вызвать `connect`.
2. Циклом `send` отправить ровно пять байтов `HELLO`, учитывая частичную
   отправку и `EINTR`. Завершающий ноль массива остаётся локальным.
3. Вывести сообщение об отправке пяти байтов в сокет.
4. Вызвать `receive_status` через тот же сокет.
5. При результате `0` сообщить о закрытии входящего потока без статуса;
   при `-1` вывести системную ошибку. Установить ненулевой `exit_code`
   и перейти к `cleanup`, не читая неинициализированную переменную статуса.
6. При получении байта проверить его значение: вывести подтверждение для
   `0x00`, сообщение об ошибке для `0x01` или об неизвестном статусе.
   Два последних случая устанавливают ненулевой `exit_code`.
7. Закрыть сокет и завершить программу.

Локальный адрес и порт клиента выбирает ядро; отдельный `bind` не требуется.
Успешный `connect` может завершиться раньше серверного `accept`;
порядок вывода сообщений в двух терминалах не фиксируется.

## 7. Функции обмена статусом и обработка ошибок

`send_status(int connection_fd, uint8_t status)` отправляет один байт
с `MSG_NOSIGNAL`. `receive_status(int connection_fd, uint8_t *status)`
принимает один байт по переданному указателю с флагами `0`.
Обе функции возвращают `ssize_t`, повторяют вызов при `EINTR`,
не выводят диагностику и не закрывают сокет.

| Результат | Отправка статуса | Получение статуса |
|---|---|---|
| `1` | Байт принят локальной системой для отправки | Байт получен, можно проверять значение |
| `0` | Отсутствие прогресса, собственная диагностика | Поток завершён без ответа, собственная диагностика |
| `-1` после обработки `EINTR` | Системная ошибка, `perror` в `main` | Системная ошибка, `perror` в `main` |

При длине в один байт положительной частичной операции нет.
Для пятибайтового сообщения хранятся счётчики `size_t`; положительный результат
увеличивает счётчик, следующая операция обрабатывает только остаток.
Результат операции проверяется до использования в расчётах.

`errno` используется для диагностики только при `-1`; нулевой результат
не задаёт системную ошибку. Все вызовы `send` используют `MSG_NOSIGNAL`:
сигнал `SIGPIPE` подавляется, но ошибки, включая `EPIPE`, проверяются.
Закрытие другой стороны не обязано проявиться первой же ошибкой отправки.

Автоматического переподключения и повторной отправки нет. Ошибка передачи,
проверки или закрытия ресурса приводит к ненулевому коду завершения.

## 8. Владение ресурсами и коды завершения

`main` каждой программы владеет полученными ею дескрипторами и закрывает
их в `cleanup`. Функции обмена статусом только используют переданный сокет.

| Программа | Ресурс | Момент получения |
|---|---|---|
| Сервер | `listen_fd` | Успешный `socket` |
| Сервер | `connection_fd` | Успешный `accept` |
| Клиент | `connect_fd` | Успешный `socket` |

При ошибке закрываются ранее полученные ресурсы. Ошибка закрытия одного
сокета не отменяет попытку закрыть остальные. После попытки `close` в Linux
дескриптор повторно не закрывается, в том числе при `EINTR`.
Ошибка очистки диагностируется и не скрывает исходную диагностику.

Код `0` клиента означает полную отправку `HELLO`, получение `0x00` и успешное
закрытие сокета. Код `0` сервера означает полное получение и проверку `HELLO`,
успешную отправку статуса и успешное закрытие обоих сокетов. Успешная отправка
статуса ошибки не делает обработку успешной.

## 9. Результаты проверок

Сборку, запуск и проверки выполняет автор в Linux/WSL. Следующие результаты
зафиксированы по его сообщениям, без самостоятельного запуска агентом:

- На первом этапе проверены установление соединения и ошибки подключения
  без сервера и привязки второго сервера к занятому адресу и порту.
- На втором этапе проверены штатная передача `HELLO`, неверное содержимое,
  накопление сообщения несколькими вызовами `recv` и закрытие после двух байтов.
  При двух байтах сервер сообщил о неполном сообщении и завершился с ошибкой.
- На этапе ответа сервера проверены штатный обмен с `0x00`, ответ `0x01`
  при неверном сообщении, закрытие сервером соединения без статуса и неизвестный
  байт статуса. Автор подтвердил ожидаемое поведение.

Закрытие без ответа проверялось временным переходом сервера к `cleanup`
после проверки `HELLO`, до отправки статуса. В итоговом коде временных
изменений проверочных сценариев нет.

Повтор после `EINTR`, частичный `send`, нулевой результат `send` при ненулевой
длине и очистка ресурсов рассмотрены по коду. Обычный успешный обмен
не подтверждает выполнение этих ветвей; отдельный запуск для их
воспроизведения не подтверждён.

## 10. Отличие от первоначального плана и дальнейшая работа

Первоначальный план этапа предусматривал попытку отправить `0x01` также при
неполном сообщении или ошибке приёма, если соединение позволяет ответить.
Текущая реализация в этих случаях сразу закрывает соединение. Клиент
распознаёт отсутствие ответа или ошибку приёма и не объявляет успех.

Документация фиксирует фактическое поведение; отправка статуса при ошибках
приёма остаётся отличием от первоначального плана. Изменение кода для этого
случая отдельно не выполнялось. Требование первой версии об ответе при ошибке,
если соединение позволяет ответить, сохраняется в README.md.

Реализованный обмен статусами и результаты проверок готовы к фиксации
отдельным коммитом. Следующий учебный этап ещё не согласован.
