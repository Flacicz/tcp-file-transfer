# Архитектура проекта

## 1. Назначение и статус

Документ описывает план второго промежуточного этапа:
передачу пяти байтов HELLO от клиента серверу по TCP.

Предыдущий этап — установление одного соединения — реализован.
По сообщению автора, проверки этого этапа в Linux пройдены.
Обмен байтами, описанный ниже, пока не реализован и не проверен.

Требования к законченной первой версии находятся в README.md.
Временные ограничения этого этапа не заменяют эти требования.

После реализации документ сверяется с кодом и обновляется
при изменении принятых решений.

## 2. Границы текущего этапа

- Целевая платформа — Linux, язык — C11.
- Клиент и сервер являются отдельными консольными программами.
- Используются блокирующие TCP-сокеты поверх IPv4.
- Обе программы работают с адресом 127.0.0.1 и портом 9000.
- Адрес и порт пока задаются в исходном коде.
- Аргументы командной строки пока не обрабатываются.
- Сервер принимает одно подключение, затем завершает работу.
- Каждая программа сообщает о событиях в свой терминал.
- Клиент передаёт заранее известное сообщение HELLO.
- Сервер получает сообщение целиком и проверяет его содержимое.
- Ответ сервера по сети, передача файлов и повторное ожидание
  клиентов добавляются на следующих этапах.
- Тайм-ауты на этом этапе не вводятся: если клиент оставляет
  соединение открытым, не передав все байты, сервер продолжает ждать.

## 3. Протокол текущего этапа

```text
Клиент → сервер: HELLO
Байты в hex:     48 45 4C 4C 4F
```

Передаются ровно пять байтов ASCII. Завершающий ноль строки C,
перевод строки и поле длины в сообщение не входят.

Длина сообщения известна обеим сторонам заранее. Граница сообщения
определяется получением пяти байтов, а не закрытием соединения.
После получения этих байтов сервер проверяет их и завершает обработку;
дополнительного чтения для ожидания EOF или проверки лишних байтов нет.

TCP сохраняет порядок байтов, но не границы вызовов отправки.
Число вызовов send и recv и размеры обработанных ими порций
могут различаться. Обе стороны учитывают фактический прогресс.

Клиент сообщает только о передаче пяти байтов своему TCP-стеку.
Это не подтверждает получение и проверку сообщения серверной программой.
Результат проверки сообщает сервер в своём терминале.
Сетевое подтверждение на этом этапе не предусмотрено.

## 4. Структура исходников и сборка

Используются существующие исходные файлы:

- client/main.c — точка входа и логика клиента.
- server/main.c — точка входа и логика сервера.

Корневой CMakeLists.txt описывает две исполняемые цели:

- client — собирается из client/main.c;
- server — собирается из server/main.c.

Результат сборки — две отдельные Linux-программы: client и server.

Для обеих целей используются C11 и предупреждения
-Wall -Wextra -Wpedantic. Для разработки выбирается Debug-сборка.
Результаты сборки размещаются отдельно от исходников.

На этом этапе логика каждой программы находится в её main.
Общие модули и дополнительные библиотеки не вводятся.
Буферы имеют фиксированный размер; динамическая память не требуется.

## 5. Последовательность работы сервера

1. Подготовить структуру локального IPv4-адреса и порта.
2. Создать сокет через socket.
3. Назначить ему локальный адрес через bind.
4. Перевести сокет в слушающее состояние через listen.
5. Вывести сообщение о готовности принимать подключение.
6. Дождаться подключения через accept.
7. Сохранить полученный дескриптор сокета соединения отдельно
   от дескриптора слушающего сокета.
8. Вывести сообщение о принятом подключении.
9. Подготовить приёмный буфер на пять байтов и счётчик полученных байтов.
10. Через recv в цикле получить ровно пять байтов в этот буфер,
    заполняя только ещё не занятую часть.
11. После полного приёма побайтно сравнить содержимое с HELLO.
12. При совпадении вывести сообщение об успешном получении и проверке.
    При несовпадении сообщить об ошибке протокола.
13. Закрыть сокет соединения и слушающий сокет.
14. Завершить программу с кодом, отражающим результат обработки
    и закрытия ресурсов.

Обмен выполняется через сокет соединения, полученный от accept.
Для recv используются флаги 0. Слушающий сокет не используется
для чтения сообщения.

Приёмный буфер содержит пять байтов данных без завершающего нуля.
Он не передаётся в вывод через %s как готовая строка C.
После успешной проверки достаточно вывести сообщение о получении HELLO.

Если поток завершился до получения всех пяти байтов,
сервер сообщает о незавершённом сообщении. При ошибке recv
полученные данные не считаются полным сообщением.

Адрес подключившегося клиента пока не извлекается.

Параметр backlog ограничивает очередь ожидающих принятия
подключений. Он не определяет количество клиентов,
обслуживаемых программой.

## 6. Последовательность работы клиента

1. Подготовить структуру адреса сервера.
2. Создать сокет через socket.
3. Попытаться установить соединение через connect.
4. При успехе вывести сообщение об установленном соединении.
5. Подготовить сообщение HELLO и счётчик отправленных байтов.
6. Через send в цикле передать ровно пять байтов,
   каждый раз указывая ещё не отправленную часть сообщения.
7. После полной отправки вывести сообщение о передаче пяти байтов в сокет.
8. Закрыть клиентский сокет.
9. Завершить программу с кодом, отражающим результат отправки
   и закрытия ресурса.

Если исходный массив инициализирован строкой "HELLO", его завершающий
ноль остаётся локальным: длина передаваемых данных равна пяти.

Во всех вызовах send используется MSG_NOSIGNAL. При соответствующей
ошибке записи это подавляет SIGPIPE; саму ошибку, например EPIPE,
клиент диагностирует по результату вызова и errno.

Локальный адрес и порт клиента выбирает ядро.
Отдельная привязка клиентского сокета через bind не требуется.

Успешный connect может завершиться раньше серверного accept.
Порядок сообщений в терминалах двух программ не фиксируется.

## 7. Учёт частичных операций

Для отправки и приёма отдельно хранятся:

- полная длина сообщения — пять байтов;
- число уже обработанных байтов;
- оставшаяся длина — полная длина минус обработанная.

Очередной вызов получает указатель на первый ещё не обработанный байт
и оставшуюся длину. Вызовы с нулевой длиной не выполняются:
при достижении пяти байтов цикл заканчивается.

Результат send или recv сохраняется в ssize_t. Размеры и счётчики
хранятся в size_t. Положительный результат используется в расчётах
только после проверки его знака.

| Результат операции | Действие |
|---|---|
| Положительное число | Увеличить счётчик на это число и продолжить с остатком |
| -1 и errno == EINTR | Повторить операцию с теми же указателем и длиной |
| -1 с другой причиной | Сообщить об ошибке и перейти к очистке |
| recv вернул 0 до получения пяти байтов | Сообщить о незавершённом сообщении и перейти к очистке |
| send вернул 0 при ненулевом остатке | Сообщить об отсутствии прогресса и перейти к очистке |

Положительный результат меньше запрошенного размера является
нормальной частичной операцией. Отправленные байты не отправляются
повторно, а полученные байты не перезаписываются следующим приёмом.

Для нулевого результата send, преждевременного EOF и несовпадения
содержимого используются собственные диагностические сообщения.
errno проверяется только после результата -1.

## 8. Владение ресурсами

| Программа | Ресурс | Когда появляется |
|---|---|---|
| Сервер | Сокет, который станет слушающим | После успешной socket |
| Сервер | Сокет соединения с клиентом | После успешного accept |
| Клиент | Клиентский сокет | После успешной socket |

Каждая программа закрывает только собственные дескрипторы.

Дескриптор считается полученным только после успешного вызова.
При ошибке освобождаются все ранее полученные ресурсы.

Очистка выполняется на всех управляемых путях завершения.
Ошибка закрытия одного дескриптора не отменяет попытку
закрыть остальные принадлежащие программе дескрипторы.

После попытки close в Linux этот номер больше не используется
программой как принадлежащий ей дескриптор. Повторный close
после ошибки, включая EINTR, не выполняется.

## 9. Ошибки и результат запуска

После ошибки основной операции программа:

1. Сохраняет сведения об ошибке.
2. Выводит сообщение с названием операции и причиной.
3. Освобождает полученные ресурсы.
4. Завершается с ненулевым кодом.

Особые случаи:

- accept, send и recv при EINTR повторяются с сохранением прогресса.
- Остальные ошибки accept на текущем этапе завершают сервер
  после очистки ресурсов.
- Неудачный connect не повторяется: клиент закрывает сокет
  и завершается.
- Ошибка обмена, незавершённое сообщение или неверное содержимое
  завершают соответствующую программу после очистки ресурсов.
- Ошибка send, включая EPIPE или ECONNRESET, диагностируется;
  новая попытка подключения и повторная отправка сообщения не выполняются.
- Ошибки close отражаются в диагностике.
- Ошибка очистки не должна скрывать исходную ошибку.

Код завершения 0 у клиента означает полную отправку сообщения
и успешное закрытие сокета. У сервера он означает получение
и проверку сообщения, а также успешное закрытие обоих сокетов.
При обнаруженной ошибке используется ненулевой код завершения.

Сообщение об установленном соединении описывает событие,
но не отменяет последующую проверку закрытия ресурсов.

Программы завершаются независимо. Например, ошибка клиента
до подключения не заставляет сервер прекратить ожидание.
Клиент также может завершиться с кодом 0, даже если сервер позднее
обнаружит ошибку: ответа с результатом обработки на этом этапе нет.

## 10. Проверка этапа

Сборку, запуск и проверки выполняет автор в одной Linux-системе,
например в WSL. Перечисленные ниже сценарии являются планом проверки
нового этапа; их результаты фиксируются после реализации.

- Обе программы собираются без предупреждений.
- Сервер без клиента сообщает о готовности и ожидает подключение.
- После запуска клиента он сообщает об отправке пяти байтов,
  сервер — о получении и проверке HELLO. Обе программы закрывают
  ресурсы и завершаются с кодом 0.
- Клиент без доступного сервера сообщает об ошибке подключения
  и завершается с ненулевым кодом.
- Второй сервер на уже занятом адресе и порту сообщает об ошибке
  привязки и освобождает созданный сокет.
- При получении пяти других байтов сервер сообщает об ошибке
  протокола и завершается с ненулевым кодом.
- При штатном закрытии отправляющей стороны без данных или после
  передачи менее пяти байтов сервер сообщает о незавершённом сообщении,
  закрывает сокеты и завершается с ненулевым кодом.
- Накопление сообщения за несколько операций приёма можно проверить,
  временно ограничив размер одного запроса recv двумя байтами.
  Сервер всё равно должен получить и проверить все пять байтов.
  После проверки временное ограничение убирается.
- Вызовы send используют MSG_NOSIGNAL, а обработка ошибки не зависит
  от гарантированного отказа первой отправки после закрытия другой стороны:
  обнаружение такого закрытия может произойти не сразу.
- По коду проверяется освобождение ресурсов на каждой ветви
  завершения, включая ветви ошибок.

Ветки EINTR, отсутствие прогресса send и положительный частичный
результат send отдельно разбираются по коду. Успешная передача
маленького сообщения сама по себе не подтверждает их выполнение.

Изменения для сценариев с неверным или неполным сообщением
выполняются только для проверки; штатный клиент передаёт HELLO.
Временные изменения не входят в итоговую реализацию этапа.

Этап завершён после проверки успешного обмена, неверного содержимого,
неполного сообщения, накопления порций и разбора оставшихся ветвей
обработки ошибок и очистки ресурсов. Проверки первого этапа также
должны продолжать проходить.
