# Архитектура проекта

## 1. Назначение и статус

Документ описывает план первого промежуточного этапа:
установление одного TCP-соединения между клиентом и сервером.

Требования к законченной первой версии находятся в README.md.
Временные ограничения этого этапа не заменяют эти требования.

После реализации документ сверяется с кодом и обновляется
при изменении принятых решений.

## 2. Границы текущего этапа

- Целевая платформа — Linux, язык — C11.
- Клиент и сервер являются отдельными консольными программами.
- Используются блокирующие TCP-сокеты поверх IPv4.
- Обе программы работают с адресом 127.0.0.1 и портом 9000.
- Адрес и порт пока задаются в исходном коде.
- Аргументы командной строки пока не обрабатываются.
- Сервер принимает одно подключение, затем завершает работу.
- Каждая программа сообщает о событиях в свой терминал.
- Данные приложения, файлы и статусы по сети пока не передаются.

## 3. Структура исходников и сборка

Планируемые исходные файлы:

- client/main.c — точка входа и логика клиента.
- server/main.c — точка входа и логика сервера.

Корневой CMakeLists.txt описывает две исполняемые цели:

- client — собирается из client/main.c;
- server — собирается из server/main.c.

Результат сборки — две отдельные Linux-программы: client и server.

Для обеих целей используются C11 и предупреждения
-Wall -Wextra -Wpedantic. Для разработки выбирается Debug-сборка.
Результаты сборки размещаются отдельно от исходников.

На этом этапе логика каждой программы находится в её main.
Общие модули и дополнительные библиотеки не вводятся.

## 4. Последовательность работы сервера

1. Подготовить структуру локального IPv4-адреса и порта.
2. Создать сокет через socket.
3. Назначить ему локальный адрес через bind.
4. Перевести сокет в слушающее состояние через listen.
5. Вывести сообщение о готовности принимать подключение.
6. Дождаться подключения через accept.
7. Сохранить полученный дескриптор сокета соединения отдельно
   от дескриптора слушающего сокета.
8. Вывести сообщение о принятом подключении.
9. Закрыть сокет соединения и слушающий сокет.
10. Завершить программу.

Адрес подключившегося клиента пока не извлекается.

Параметр backlog ограничивает очередь ожидающих принятия
подключений. Он не определяет количество клиентов,
обслуживаемых программой.

## 5. Последовательность работы клиента

1. Подготовить структуру адреса сервера.
2. Создать сокет через socket.
3. Попытаться установить соединение через connect.
4. При успехе вывести сообщение об установленном соединении.
5. Закрыть клиентский сокет.
6. Завершить программу.

Локальный адрес и порт клиента выбирает ядро.
Отдельная привязка клиентского сокета через bind не требуется.

Успешный connect может завершиться раньше серверного accept.
Порядок сообщений в терминалах двух программ не фиксируется.

## 6. Владение ресурсами

| Программа | Ресурс | Когда появляется |
|---|---|---|
| Сервер | Сокет, который станет слушающим | После успешной socket |
| Сервер | Сокет соединения с клиентом | После успешного accept |
| Клиент | Клиентский сокет | После успешной socket |

Каждая программа закрывает только собственные дескрипторы.

Дескриптор считается полученным только после успешного вызова.
При ошибке освобождаются все ранее полученные ресурсы.

Очистка выполняется на всех управляемых путях завершения.
Ошибка закрытия одного дескриптора не отменяет попытку
закрыть остальные принадлежащие программе дескрипторы.

После попытки close в Linux этот номер больше не используется
программой как принадлежащий ей дескриптор. Повторный close
после ошибки, включая EINTR, не выполняется.

## 7. Ошибки и результат запуска

После ошибки основной операции программа:

1. Сохраняет сведения об ошибке.
2. Выводит сообщение с названием операции и причиной.
3. Освобождает полученные ресурсы.
4. Завершается с ненулевым кодом.

Особые случаи:

- accept при EINTR повторяется.
- Остальные ошибки accept на текущем этапе завершают сервер
  после очистки ресурсов.
- Неудачный connect не повторяется: клиент закрывает сокет
  и завершается.
- Ошибки close отражаются в диагностике.
- Ошибка очистки не должна скрывать исходную ошибку.

Код завершения 0 означает успешное выполнение этапа
и успешное закрытие ресурсов. При обнаруженной ошибке
используется ненулевой код завершения.

Сообщение об установленном соединении описывает событие,
но не отменяет последующую проверку закрытия ресурсов.

Программы завершаются независимо. Например, ошибка клиента
до подключения не заставляет сервер прекратить ожидание.

## 8. Проверка этапа

Проверки выполняются в одной Linux-системе, например в WSL.

- Обе программы собираются без предупреждений.
- Сервер без клиента сообщает о готовности и ожидает подключение.
- После запуска клиента обе стороны сообщают о соединении,
  закрывают ресурсы и завершаются с кодом 0.
- Клиент без доступного сервера сообщает об ошибке подключения
  и завершается с ненулевым кодом.
- Второй сервер на уже занятом адресе и порту сообщает об ошибке
  привязки и освобождает созданный сокет.
- По коду проверяется освобождение ресурсов на каждой ветви
  завершения, включая ветви ошибок.

Проверки обрывов при передаче данных добавляются на этапе обмена.
Успешное закрытие сокета не считается проверкой доступности
другой стороны.
